1. ROS 2 TOPIC IDENTIFICATION
================================================================================

1.1 ODOMETRY TOPIC
------------------
Topic Name: /odom
Message Type: nav_msgs/msg/Odometry
Direction: GZ_TO_ROS (Gazebo → ROS 2)
Bridge Config: ros_gz_bridge.yaml (line 15-19)
Source: Gazebo OdometryPublisher plugin (model.sdf line 736-742)
Frame ID: odom
Child Frame ID: saye/base_link
Publish Rate: Real-time (from Gazebo simulation)
TF Publishing: Yes (publish_tf=true in plugin)
Notes: 
  - Published by gz-sim-odometry-publisher-system plugin
  - Provides 3D odometry (dimensions=3)
  - TF transform odom→saye/base_link published by plugin
  - Additional odom→saye transform published by odom_to_tf.py script
  - Used by Nav2, AMCL, and SLAM for localization

1.2 LASER SCAN TOPIC
--------------------
Topic Name: /scan
Message Type: sensor_msgs/msg/LaserScan
Direction: GZ_TO_ROS (Gazebo → ROS 2)
Bridge Config: ros_gz_bridge.yaml (line 21-25)
Source: Gazebo GPU LiDAR sensor (model.sdf line 142-173)
Frame ID: saye/base_link (via gz_frame_id)
Sensor Name: gpu_lidar
Specifications:
  - Horizontal: 720 samples, 360° coverage (-3.1459 to 3.1459 rad)
  - Vertical: 12 samples, 30° coverage (-0.261799 to 0.261799 rad)
  - Range: 0.3m to 50m
  - Update Rate: 10 Hz
  - Noise: Gaussian, stddev=0.01
Notes:
  - Used by SLAM (slam_toolbox) for mapping
  - Used by Nav2 costmaps for obstacle avoidance
  - Used by AMCL for localization
  - Primary sensor for DRL observation space

1.3 VELOCITY COMMAND TOPIC
---------------------------
Topic Name: /cmd_vel
Message Type: geometry_msgs/msg/Twist
Direction: BIDIRECTIONAL (ROS 2 ↔ Gazebo)
Bridge Config: ros_gz_bridge.yaml (line 2-6)
Sink: Gazebo AckermannSteering plugin (model.sdf line 708-727)
Control Fields:
  - linear.x: Forward/backward velocity (m/s)
    Range: -10.0 to 10.0 m/s (per plugin config)
  - angular.z: Angular velocity (rad/s)
    Converted to steering angle by AckermannSteering plugin
Notes:
  - This is the PRIMARY control interface for DRL
  - AckermannSteering plugin converts Twist to wheel velocities and steering angles
  - No separate steering topic exists - steering is derived from angular.z
  - Nav2 controller_server publishes to this topic during autonomous navigation
  - Can be overridden by DRL agent

1.4 STEERING TOPIC
------------------
Topic Name: NONE (No separate steering topic)
Implementation: Internal to AckermannSteering plugin
Steering Joints:
  - front_left_wheel_steering_joint (revolute, limit: ±0.6 rad)
  - front_right_wheel_steering_joint (revolute, limit: ±0.6 rad)
Steering Limit: 0.4 rad (~23 degrees) - configured in plugin
Control Method: Derived from /cmd_vel angular.z via AckermannSteering plugin
Notes:
  - Steering is NOT directly controllable via ROS topic
  - Steering angles are computed internally by plugin from cmd_vel
  - Joint states available via /joint_states topic (if needed)
  - DRL should only publish to /cmd_vel, not attempt to control steering directly

1.5 ADDITIONAL SENSOR TOPICS
----------------------------
IMU Topic: /imu
  - Type: sensor_msgs/msg/Imu
  - Direction: GZ_TO_ROS
  - Update Rate: 50 Hz
  - Frame: saye/base_link
  - Used by: saye_localization (Kalman filter)

Camera Topics:
  - /camera/front_raw: Front camera (sensor_msgs/msg/Image)
  - Other cameras available but commented out in bridge config

TF Topic: /tf
  - Type: tf2_msgs/msg/TFMessage
  - Direction: GZ_TO_ROS

2. TF FRAME IDENTIFICATION
================================================================================

2.1 TF FRAME TREE
-----------------
Complete TF Chain:
  map (global frame)
    └── odom (odometry frame, from Gazebo OdometryPublisher)
        └── saye (robot namespace frame, from robot_state_publisher)
            └── saye/base_link (robot base frame)
                ├── saye/front_left_wheel_steering_link
                ├── saye/front_right_wheel_steering_link
                ├── saye/front_left_wheel_link
                ├── saye/front_right_wheel_link
                ├── saye/rear_left_wheel_link
                ├── saye/rear_right_wheel_link
                └── saye/lidar_link (LiDAR frame, referenced in nav2_params)

2.2 FRAME DETAILS
-----------------
map:
  - Global fixed frame
  - Origin: Defined by SLAM or map server
  - Published by: SLAM (slam_toolbox) or AMCL
  - Used by: Nav2 for global planning

odom:
  - Odometry frame (drift-free short-term)
  - Origin: Initial robot position
  - Published by: 
    * Gazebo OdometryPublisher plugin (odom→saye/base_link)
    * odom_to_tf.py script (odom→saye, for SLAM compatibility)
  - Updated by: Gazebo physics simulation

saye:
  - Robot namespace frame (frame_prefix in robot_state_publisher)
  - Purpose: Namespace isolation (supports multi-robot, but we use single robot)
  - Published by: robot_state_publisher
  - Note: This is the frame_prefix, actual base is saye/base_link

saye/base_link:
  - Robot base frame (center of robot)
  - Origin: Robot center (approximately 0.1371m forward from geometric center)
  - Published by: robot_state_publisher from URDF
  - Used by: All sensors, Nav2, AMCL, SLAM

saye/lidar_link:
  - LiDAR sensor frame
  - Position: 0.05m forward, 0.106m up from base_link
  - Referenced in: nav2_params.yaml (scan_frame_id)

2.3 TF PUBLISHERS
-----------------
1. Gazebo OdometryPublisher plugin:
   - Publishes: odom → saye/base_link
   - Config: model.sdf line 736-742

2. odom_to_tf.py script:
   - Publishes: odom → saye
   - Purpose: Connect TF chain for SLAM (when odometry doesn't publish saye frame)
   - Used in: slam.launch.py, slam_navigation.launch.py

3. robot_state_publisher:
   - Publishes: saye → saye/base_link (and all joint transforms)
   - Source: URDF file (saye.urdf)
   - Config: saye_spawn.launch.py line 97-105

4. SLAM (slam_toolbox):
   - Publishes: map → odom
   - Used when: Running SLAM mode

5. AMCL:
   - Publishes: map → odom
   - Used when: Running navigation with pre-built map

4. DRL INTEGRATION POINTS
================================================================================

4.1 OBSERVATION SPACE (INPUTS TO DRL)
--------------------------------------
Primary Sensors:
  1. /scan (LaserScan)
     - Type: sensor_msgs/msg/LaserScan
     - Dimensions: 720 horizontal samples, 12 vertical samples
     - Range: 0.3m to 50m
     - Update Rate: 10 Hz
     - Usage: Obstacle detection, distance measurements

  2. /odom (Odometry)
     - Type: nav_msgs/msg/Odometry
     - Information: Position, velocity, orientation
     - Frame: odom → saye/base_link
     - Usage: Current state, velocity feedback

  3. /imu (IMU)
     - Type: sensor_msgs/msg/Imu
     - Information: Angular velocity, linear acceleration
     - Update Rate: 50 Hz
     - Usage: Orientation, acceleration feedback

  4. /camera/front_raw (Camera)
     - Type: sensor_msgs/msg/Image
     - Resolution: 720x1080
     - Format: R8G8B8
     - Usage: Visual perception (optional for DRL)

  5. TF Tree
     - Frames: map, odom, saye/base_link
     - Usage: Localization, relative positioning
     - Access: tf2_ros::Buffer

Secondary Information:
  - /map (OccupancyGrid): If using pre-built map
  - /goal_pose: If using Nav2 goal interface
  - /plan: If monitoring Nav2 path planning

4.2 ACTION SPACE (OUTPUTS FROM DRL)
------------------------------------
Primary Control Interface:
  Topic: /cmd_vel
  Type: geometry_msgs/msg/Twist
  Fields:
    - linear.x: Forward velocity (m/s)
      Range: -10.0 to 10.0 m/s (plugin limits)
      Recommended: -2.0 to 2.0 m/s for realistic driving
    - angular.z: Angular velocity (rad/s)
      Range: Limited by steering constraints
      Conversion: Plugin converts to steering angle via Ackermann geometry
      Recommended: -1.0 to 1.0 rad/s for smooth steering

Steering Control:
  - NO direct steering topic
  - Steering derived from angular.z by AckermannSteering plugin
  - Steering limit: ±0.4 rad (±23 degrees)
  - Wheel base: 0.2255 m
  - Wheel separation: 0.2 m

4.3 DRL INTEGRATION ARCHITECTURE
---------------------------------
Recommended DRL Node Structure:
  1. Subscriptions:
     - /scan (LaserScan) → Observation preprocessing
     - /odom (Odometry) → State estimation
     - /imu (IMU) → Orientation/acceleration (optional)
     - /camera/front_raw (Image) → Visual input (optional)
     - TF listener → Localization

  2. Publishers:
     - /cmd_vel (Twist) → Control commands
     - Optional: /drl/debug (custom messages for debugging)

  3. Services (Optional):
     - /reset_simulation → Reset robot pose
     - /pause_simulation → Pause/resume training

  4. Integration Points:
     - Can run alongside Nav2 (DRL overrides /cmd_vel)
     - Can run standalone (DRL is primary controller)
     - Should disable Nav2 controller_server when training DRL

4.4 SAFE DRL INTEGRATION REQUIREMENTS
--------------------------------------
1. Topic Isolation:
   - DRL agent should publish to /cmd_vel
   - Ensure Nav2 controller_server is NOT running during training
   - Or use topic remapping to separate DRL and Nav2 control

2. Safety Constraints:
   - Respect velocity limits: -10.0 to 10.0 m/s
   - Respect steering limits: ±0.4 rad
   - Implement emergency stop (e.g., on collision detection)
   - Monitor /scan for obstacle proximity

3. Frame Consistency:
   - All observations should use consistent frame (saye/base_link or odom)
   - TF lookups should handle frame not found errors
   - Account for frame_prefix "saye/" in all frame names

4. Simulation State:
   - Use use_sim_time:=true for all nodes
   - Synchronize with Gazebo clock
   - Handle simulation reset gracefully

5. Training Environment:
   - Can spawn robot at different locations for training diversity
   - Use OSM spawn points for varied starting positions
   - Reset robot pose via Gazebo service or launch file

6. ARCHITECTURE SUMMARY
================================================================================

6.1 SYSTEM OVERVIEW
-------------------
This is a ROS 2 Jazzy + Gazebo Harmonic simulation stack for an Ackermann
steering vehicle (single robot, named "saye") operating in a 3D city
environment (Bari, Italy) generated from OpenStreetMap data.

Key Components:
  1. Gazebo Harmonic: Physics simulation engine
  2. ROS 2 Jazzy: Middleware and communication
  3. ros_gz_bridge: Bidirectional topic/service bridge
  4. Nav2: Navigation stack (optional, can be disabled for DRL)
  5. SLAM: Mapping capability (slam_toolbox)
  6. OSM Pipeline: City generation from OpenStreetMap

6.2 DATA FLOW
-------------
Sensor Data Flow (Gazebo → ROS 2):
  Gazebo Sensors → ros_gz_bridge → ROS 2 Topics
    - LiDAR → /scan
    - IMU → /imu
    - Odometry → /odom
    - Cameras → /camera/*
    - Joint States → /joint_states

Control Data Flow (ROS 2 → Gazebo):
  ROS 2 Topics → ros_gz_bridge → Gazebo Plugins
    - /cmd_vel → AckermannSteering plugin → Wheel joints

TF Flow:
  Gazebo → odom → saye/base_link (via OdometryPublisher)
  URDF → saye → saye/base_link (via robot_state_publisher)
  SLAM/AMCL → map → odom

6.3 PACKAGE STRUCTURE
---------------------
saye_bringup:
  - Launch files, configs, maps, RViz configs
  - Entry point: saye_spawn.launch.py

saye_description:
  - URDF, SDF models, world files
  - Robot model: models/saye/model.sdf
  - World: worlds/bari_world.sdf

saye_control:
  - Control nodes (currently joystick controller)
  - DRL agent will integrate here or as separate package

saye_localization:
  - Kalman filter for odometry fusion
  - Optional enhancement to Gazebo odometry

saye_msgs:
  - Custom messages (Map.msg, ShareMap.srv)

saye_behaviortree:
  - Behavior tree package (for future use)

6.4 DRL INTEGRATION ARCHITECTURE
---------------------------------
Recommended Structure:
  saye_drl/ (new package)
    ├── nodes/
    │   └── drl_agent_node.py/cpp
    ├── config/
    │   └── drl_params.yaml
    ├── launch/
    │   └── drl_training.launch.py
    └── CMakeLists.txt, package.xml

Integration Points:
  1. Observation: Subscribe to /scan, /odom, /imu, TF
  2. Action: Publish to /cmd_vel
  3. Reward: Monitor /odom, /scan, collision topics
  4. Reset: Gazebo service or spawn node

Launch Integration:
  - Option 1: DRL standalone (disable Nav2)
  - Option 2: DRL + Nav2 (DRL overrides, Nav2 as fallback)
  - Option 3: DRL training mode (fast reset, no GUI)
